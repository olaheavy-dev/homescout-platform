## Question 1 (FE-01): routing and rendering
**You choose:** whether the prototype is built as plain files (A) or needs a running server from the start (B).
- **A. App Router with a static export now, server mode later (recommended).** `output: 'export'` makes `next build` write plain HTML, CSS and JavaScript to `out/`, which any static host or a local folder can serve. Server Components still run, but at build time, which suits fixtures: pages read the JSON at build. `/homes/[home-slug]` works through `generateStaticParams` from `homes.json`, and so must every nested dynamic route (for example `/homes/[home-slug]/nearby/[topic]`, from the topic list), with `dynamicParams` off; the `/area` fragment is read in the browser. Next.js documents this as "start as a static site … then later optionally upgrade to use features that require a server". *Limits (Next.js docs):* no route handlers that read the request, no headers, redirects or rewrites, no proxy, no Server Actions, no default image optimisation. So security headers (CSP) are set by the host (IN-02), and images are prepared at their display size. *Strict CSP:* nonces need dynamic rendering ([Next.js CSP guide](https://nextjs.org/docs/app/guides/content-security-policy)), so a static export can't use them; a CSP without `'unsafe-inline'` would then rely on Next.js's experimental Subresource Integrity, and the small inline script that sets the theme before the page paints would need its hash in the policy. Settled with IN-02 and the security headers, not here. *Postcode rule:* nothing runs on a server, and a fragment is never sent to one, so 0046 holds by construction. *Later:* CopilotKit's runtime is a Next.js route handler answering GET and POST (`app/api/copilotkit/route.ts`, per [CopilotKit's guide](https://docs.copilotkit.ai/ms-agent-dotnet)), which static export doesn't support. When the first such route is needed (stage 6 chat, or earlier if IN-02 picks a Node host) the app switches to server output: a configuration change, not a rewrite. *Cost:* zero to host; *learning:* the App Router is what current Next.js and React documentation teaches (Server and Client Components, layouts).
  - *Query parameters (the trade-off of a static export).* Most routes in the information architecture use `?story=`, `?step=`, `?homes=` or `?q=`. A static page can't know them at build time: a Client Component that reads them with `useSearchParams` is rendered in the browser up to the nearest `<Suspense>` boundary, and the build fails if there is none ([`useSearchParams`](https://nextjs.org/docs/app/api-reference/functions/use-search-params)). So the step-specific part isn't in the HTML, the fixture data for every step is sent to the browser, and swapping the placeholder for the content risks the CLS 0.1 and 170 KB budgets. Three ways round it:
    - **(a) Read them in the browser inside `<Suspense>`, with a placeholder the same size as the content (recommended for now).** Keeps the agreed URLs and `@ui` scenarios. The fixtures are small; size-limit and Lighthouse CI in #86 show whether the budgets hold.
    - **(b) Story and step as path segments** (for example `/move/buyer/1`) built by `generateStaticParams`: every step is real HTML, but it changes the information architecture's URL contract and the `@ui` scenarios that use it. The fallback if (a) misses a budget.
    - **(c) Server output** (option B): the server reads the parameters on each request; needs a running host.
- **B. App Router with server rendering from day one.** Everything works, including route handlers, but the private preview needs a running Node server (a running cost and an IN-02 decision, founder-only) and makes it easy to add server code before stage 5b says there is a backend.
- **C. Pages Router.** "Still supported and being improved" (Next.js docs), but no Server Components, and the information architecture is already written for the App Router. Not recommended: less learning value for current React.

## Question 2 (FE-02): styling and components
**You choose:** plain CSS files or Tailwind for styling, and which library (if any) supplies the hard accessible widgets.
**Styling.**
- **A. CSS Modules reading the custom properties in `tokens.css` (recommended).** `tokens.css` becomes the app's global stylesheet; each component has a `.module.css` file that uses only `var(--…)` tokens. Light and dark already work through `[data-theme]` and `prefers-color-scheme` in that file. No new package (built into Next.js). Teaches plain CSS, which outlasts any framework. Risk: nothing stops a hard-coded colour, so the lint step below forbids raw colour values in module files.
- **B. Tailwind CSS v4 mapped to the tokens.** Next.js's CSS page recommends it. Each token would be mirrored in `@theme inline { --color-…: var(--color-…) }`, with `--color-*: initial` to remove Tailwind's own palette (Tailwind theme docs), and a custom dark variant for `[data-theme]` (that syntax is on Tailwind's dark-mode page, not checked here). Faster to write once learned, but two names for every token, long class lists for a beginner to read, and two packages (`tailwindcss`, `@tailwindcss/postcss`).
- **Other (Sass, CSS-in-JS):** adds a package with no gain over tokens already written as custom properties. Not recommended.

**Components.**
- **A. Own components on native HTML only.** Smallest bundle; native `<dialog>`, `<details>` and form controls cover sheets, disclosures and inputs. But the address combobox (B10), tabs, menus and tooltips must then be built and tested for keyboard and screen readers by hand, which is where accessibility bugs usually live.
- **B. Own components, with React Aria Components for the hard widgets (recommended).** Unstyled ("React Aria does not include any styles by default"), styled through class names and state data attributes, so CSS Modules and the tokens style it. Its overview says semantics and keyboard behaviour follow the W3C ARIA Authoring Practices and are "extensively tested using many popular screen readers", with localised number and date formatting (useful for en-GB). Includes ComboBox, Select, Menu, Dialog and Tooltip. Simple parts (buttons, cards, status tags) stay plain HTML.
- **C. Own components with Radix Primitives.** Also unstyled and following WAI-ARIA patterns "where possible", with one tree-shakeable `radix-ui` package. We found no combobox in its published primitive list, and B10 needs one.

## Question 3 (FE-04): frontend checks
**You choose:** only the lint tool (ESLint and Prettier, or Biome). The rest follows Next.js's own guides or earlier founder approvals and is listed so it becomes pre-approved.
- **Unit and component tests: Vitest with React Testing Library** (the setup in Next.js's own Vitest guide). Fast checks of components and formatting helpers in jsdom. Vitest can't render `async` Server Components (Next.js docs), so pages are proved by the `@ui` browser scenarios instead. Alternative: browser tests only, which is slower and gives the founder no small examples to learn from.
- **Lint and format:** *A. ESLint with `eslint-config-next` and Prettier (recommended):* what Next.js documents (`next lint` was removed in Next.js 16; the ESLint CLI is used), and `eslint-config-next` brings the React, hooks and Next.js rule sets and includes the `jsx-a11y` accessibility plugin. **Pin ESLint 9, not 10:** `eslint-config-next` accepts ESLint ≥ 9, but plugins it bundles (`eslint-plugin-jsx-a11y` 6.10, `eslint-plugin-react` 7.37, `eslint-plugin-import` 2.32) declare ESLint only up to 9 as a peer (npm registry). Move to 10 when they do. Prettier formats only `apps/web`, so the Markdown docs are untouched. *B. Biome:* one fast tool and package with `next` and `react` rule domains (13 Next.js rules, 9 recommended), and it doesn't depend on the TypeScript compiler API; but Next.js documents only ESLint, so a learner gets fewer matching examples. A reasonable later swap. A stylelint rule set is not proposed; the "no raw colours" rule is a small ESLint or script check decided in #86.
- **Type checking:** `tsc --noEmit` with `strict: true`. **Pin TypeScript 6.0, not 7:** `typescript-eslint` (used by `eslint-config-next/typescript`) declares `typescript >=4.8.4 <6.1.0`, and TypeScript 7 doesn't yet offer the compiler API that tool uses (Next.js docs). Move to 7 when `typescript-eslint` supports it.
- **Fixture types generated from the JSON Schemas:** `json-schema-to-typescript` (`json2ts`) writes `.d.ts` files from `packages/fixtures/schema/` (`$ref` to other files is followed). They are committed and `make generated-check` fails if they are stale, like `costs.json`. *Limits (its README):* `if`/`then`/`else` are ignored ("properties and `required` inside the branches contribute nothing"), so our 47 conditional rules add nothing to the types; `dependentRequired` (2 uses) can't be expressed in TypeScript, and `dependentSchemas` (2 uses, in the test-case schema) isn't supported; keywords that only constrain values (ranges, patterns) are dropped. By default each schema file is compiled on its own, so a type shared between files is declared again in each output file; sharing them needs the experimental `--imports` option. It resolves a `$ref` against the working folder, not the schema's `$id`, so #86 runs it from `packages/fixtures/schema/` (`--cwd`). So the types are looser than the schemas. The schema validator in `make check` stays the source of truth; the types are a convenience, and data is never hand-typed. API types later come from OpenAPI (0042).
- **Automated accessibility:** axe in the browser, through `Deque.AxeCore.Playwright` inside the Reqnroll `@ui` scenarios (0043), run on the component gallery (#150) and each screen in both themes, failing on WCAG 2.0–2.2 A and AA rules. Not in jsdom, which has no layout, so it can't check colour contrast. axe finds "on average 57% of WCAG issues" (axe-core README); B16's manual keyboard and screen-reader pass stays.
- **en-GB copy, money and dates (follows the brief and rules 2 and 7).** Money is stored in pence and shown with `Intl.NumberFormat('en-GB', { style: 'currency', currency: 'GBP' })` on the pence divided by 100, always with both decimal places, so nothing is rounded; the pence part is styled a step smaller and lighter through `formatToParts` (craft sheet). This is formatting, not calculation (rule 2), in the same way that distances are shown exactly as recorded (area decision 7, `.design/prototype/research/area-display-summary.md`). A missing figure is shown as missing, never as £0.00 (rule 7). Dates use `Intl.DateTimeFormat('en-GB')`. One small helper module holds these, with Vitest tests.
- **Folder structure (default, easy to change):** `apps/web/app` for routes, `apps/web/components` for components with their `.module.css` files, `apps/web/lib` for fixture loading and formatting, and `apps/web/styles/tokens.css`. #86's plan confirms it as a register line.
- **Performance budgets:** the founder **approved** `@lhci/cli` and `size-limit` (with `@size-limit/preset-app`) on 11 Nov 2026, together with `json-schema-to-typescript`, `Deque.AxeCore.Playwright` and `maplibre-gl` (`.design/prototype/research/area-display-summary.md`, "Packages approved by the founder"). That approval isn't on a pre-approved list `AGENTS.md` names (0035, 0042, 0043 or a register line), so this record names them to put them there; MapLibre is left to FE-03. `size-limit` with **`@size-limit/file`** measures the gzip size of the built route chunks. `@size-limit/file` is part of the approved `@size-limit/preset-app`; the preset also adds `@size-limit/time`, which runs the code in a headless browser (through `estimo`) to estimate run time, and Lighthouse CI already measures timing, so the smaller plugin is enough; `@lhci/cli` runs Lighthouse on the static `out/` folder (`staticDistDir`) with assertions for LCP, CLS and Total Blocking Time (the lab stand-in for INP). Both join `make check` when B18 is built.
- **How `make check` and CI run them:** Node 26 pinned (`.nvmrc` and `engines`), npm with `package-lock.json` and `npm ci` (locked, like NuGet). New Make steps in the same order as today: `restore` adds `npm ci`; `format-check` adds Prettier; a `lint` step runs ESLint and `tsc`; `generated-check` covers the fixture types; `test` adds `vitest run`; a `web-build` step runs `next build`. CI adds `actions/setup-node` (pinned by SHA) and Dependabot's npm ecosystem, with an `npm-zero-x` group for `@lhci/cli` (like `actions-zero-x`), so its minor updates go to full review under the merge rule for `0.x` packages. Adding JavaScript/TypeScript to CodeQL's default setup ([0027](0027-stage-2-engineering-hardening.md)) is a repository setting, so the founder changes it. From #86, `@ui` scenarios run against the built `out/` folder; how the test project serves it (for example ASP.NET Core static files, already in the .NET shared framework) is settled in #86's plan, with no new package.

## Decision
The founder chose on 12 Nov 2026, in answer to the questions above:
- **FE-01: option B, the App Router with server rendering, run locally only.** The founder asked why the preview would be deployed at all; under 0045 it may stay local, and then a running server costs nothing. **Stage 5 runs only on the founder's machine and in CI** (`next dev`, or `next build` then `next start`); hosting is decided once at stage 5b with IN-01 to IN-05, for the public area check (0046). What this changes from the analysis above:
  - pages read `?story=`, `?step=`, `?homes=` and `?q=` on the server through the page's `searchParams` prop, so the static-export trade-off and options (a) to (c) no longer apply;
  - `@ui` scenarios and Lighthouse CI run against `next start` instead of an `out/` folder (Lighthouse CI's `startServerCommand` and a URL in place of `staticDistDir`); Make's `web-build` step runs `next build`, so `make check` needs Node, `npm ci` and the build before the `@ui` scenarios. How the test project starts `next start`, waits until it is ready and stops it is settled in #86's plan;
  - the postcode rule still holds, because a URL fragment is never sent to a server;
  - **no backend before stage 5b** (0046): no route handlers, Server Actions or proxy that fetch or store data until then; server components only read the committed fixtures. A reviewer treats a breach as P1;
  - security headers, including a nonce-based strict CSP, become possible on a server and are decided with hosting at stage 5b;
  - if the app is ever hosted, it needs a Node host rather than a free static one (an IN-02 cost, founder-only);
  - **IN-01 to IN-05 move to stage 5b**, where the public area check (0046) needs hosting anyway, so they are decided once. Until then nothing is deployed and nothing runs up a cost, so the stage 4 gate (#84) no longer waits for IN records or a budget cap, and question 5's last sentence ("the stage 4 gate still needs the IN records before the first deployment") no longer applies: the first deployment is at stage 5b, after IN-05. Every stage 5 slice runs locally and in CI; the stage 5 gate is met on the local app.
- **FE-02: Tailwind CSS v4 with React Aria Components.** Styling uses Tailwind utility classes on the tokens, not CSS Modules:
  - packages from Tailwind's [Next.js guide](https://tailwindcss.com/docs/installation/framework-guides/nextjs): `tailwindcss`, `@tailwindcss/postcss` and `postcss` (all MIT; 4.3 and 8.5), with `postcss.config.mjs` and `@import "tailwindcss"` in the global stylesheet;
  - Tailwind's whole default theme is removed with `--*: initial` ([theme variables](https://tailwindcss.com/docs/theme)), and every token group in `tokens.css` (colours, type sizes, fonts, spacing, radii, shadows, easing) is mapped once in `@theme inline` under Tailwind's names, for example `--color-surface: var(--color-bg-primary)`. Then only Vestagraph values exist as classes: a default such as `rounded-lg` (8 px, not one of the token radii 6, 10, 16 and 24) simply doesn't exist. A Tailwind name never repeats the token's own name, which would point the variable at itself;
  - breakpoints are the one allowed copy: CSS doesn't allow `var()` inside a media query, so the five `--breakpoint-*` values are written as literals in `@theme`, with a test that they equal `tokens.css`;
  - light and dark switch inside `tokens.css` (`[data-theme]` and `prefers-color-scheme`), so a class such as `bg-surface` changes with the theme without `dark:` classes. If a `dark:` variant is ever needed, a `@custom-variant` matches the tokens' rules: Tailwind's [dark-mode page](https://tailwindcss.com/docs/dark-mode) documents the `[data-theme=dark]` form but not combined with the system preference, so #86 tests that;
  - React Aria states are styled with Tailwind's data-attribute variants, for example `data-[selected]:…` ([React Aria styling](https://react-aria.adobe.com/styling)); its optional Tailwind plugin is not adopted;
  - the "no raw colours" check now forbids arbitrary values such as `bg-[#…]` or `text-[13px]` (settled in #86's plan).
- **FE-04: as listed**, with ESLint 9 and Prettier, TypeScript 6.0 and `@size-limit/file`.
- **DS-01, DS-02: code-first.**
- **Order:** #86 starts after the stage 3 gate (#71), before the stage 4 gate (#84), as question 5 describes. The founder chose "screens first, local": the screens are built on sample data, and live area data follows at stage 5b without rebuilding them.

**Packages named by this decision** (pre-approved, under 0042's licence and documentation checks): the list under Recommendation, plus `tailwindcss`, `@tailwindcss/postcss` and `postcss`.
